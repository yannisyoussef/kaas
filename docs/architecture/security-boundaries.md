# Security Boundaries

**Status: CONTROL-PLANE IDENTITY AND TENANT CONTROLS IMPLEMENTED. SANDBOX CONTROLS IMPLEMENTED AND EVIDENCED FOR A TRUSTED PROBE ([ADR-022](../adr/022-hostile-execution-boundary-and-synthetic-probe.md)). EXECUTION AUTHORIZATION IMPLEMENTED ([ADR-023](../adr/023-execution-authorization-and-assignment-scoped-capabilities.md)).** Arbitrary execution is disabled, and no ExecutionCommand is executed.

**Two independent gates now stand between a claimed run and execution, and neither substitutes for the other.**
A sandbox that provably confines what it runs is not permission to run anything, and a valid assignment-scoped
authorization is worthless if the boundary it names cannot be shown to hold. Execution requires both: an
approved sandbox boundary AND a live, assignment-scoped authorization. Treating a secure sandbox as permission
is the specific mistake this separation exists to prevent.

1. **Identity boundary (implemented):** Spring Security validates external RS256 JWT signature, issuer, audience, time claims, subject, and one UUID organization claim. Product endpoints have no anonymous or local bypass.
2. **Control/execution boundary:** API validates and persists intent; it never loads or executes user feature code.
3. **Worker/sandbox boundary (implemented and evidenced for a trusted probe):** a fresh non-root container with read-only root filesystem, all Linux capabilities dropped, no-new-privileges, no privileged mode, CPU/memory/PID/wall-clock limits, a bounded `noexec` temporary workspace, and bounded output on both the collector and the host log. Under `DENY_ALL` it also has **no network at all**, which remains the simpler proven path and the one a run needing no network keeps using.
4. **Execution egress boundary (implemented and evidenced for a trusted workload):** under `ALLOWLIST` the sandbox is attached to exactly one per-execution `--internal` network whose only other member is a trusted proxy. It is not a URL check followed by ordinary container networking, and it is not `iptables` inside the sandbox: the sandbox has no second route because no such route exists, so nothing in its own configuration is asked to cooperate. The proxy authorizes every request against authoritative state, resolves the destination once, classifies every returned address, and connects to that exact address; an established tunnel is revalidated on a timer and closed within a documented **polling** bound after its assignment is fenced. `ALLOWLIST` is refused — never downgraded — unless the deployment's own assessment carries the five egress controls passing, and the runner refuses independently of the control plane. See [ADR-026](../adr/026-enforceable-assignment-scoped-execution-egress.md) and [enforceable-execution-egress.md](enforceable-execution-egress.md).
   An earlier version of this document claimed allowlisted egress at a time when the platform would not authorize one, and a later version said no launcher could ever enforce one. Both are now superseded by a mechanism with executable evidence behind it.
5. **Execution authorization boundary (implemented):** owning an attempt is not permission to execute it. An `ExecutionAuthorization` is a separate decision, scoped to one attempt and assignment epoch and one worker identity, bounded by the lease that justifies it, and revalidated against authoritative state on every capability redemption — so cancellation, fencing, epoch supersession, and lease loss each make an unexpired token useless. Capabilities are short-lived bearer tokens whose plaintext is never stored. See [ADR-023](../adr/023-execution-authorization-and-assignment-scoped-capabilities.md).
6. **Secret boundary (metadata implemented, delivery absent, capability envelope designed):** the control plane stores only project-scoped SecretReference identity/name/audit metadata and EnvironmentRevision bindings. It has no value, ciphertext, provider/path, credential, resolve, reveal, or redemption field/endpoint. A UUID grants no authority. Future runtime capabilities require a separate reviewed subsystem and must never derive authority from metadata possession.
7. **Tenant boundary (implemented for current control-plane resources):** every repository query uses the trusted organization plus full project/parent hierarchy. Composite foreign keys enforce ownership for Projects, Features/Revisions, SecretReferences, Environments/Revisions, and RunProfiles/Revisions; cross-tenant/missing resources share concealed 404 behavior.
8. **Artifact boundary:** use opaque keys, content-type allowlists, size limits, malware scanning policy, and signed/authorized access.

Problem Details and correlated logging avoid credentials, tokens, feature/configuration values, secret-reference IDs, idempotency keys, SQL internals, and sensitive request bodies. Configuration responses use `Cache-Control: no-store`. Docker alone must not be treated as proof of hostile-code safety. See [project-feature-slice.md](project-feature-slice.md) and [environment-run-profile-slice.md](environment-run-profile-slice.md) for implemented boundaries.
