# ADR-007: Bounded durable SSE replay for run events

## Status

PROPOSED

## Context

Clients need one-way progress for asynchronous runs. Reconnects, proxies, authentication expiry, event retention, and terminal streams must have deterministic behavior. Persisting raw logs or every Karate step would create amplification, redaction, and storage risk. No SSE implementation exists.

## Decision

Use `GET /api/v1/runs/{runId}/events` as a proposed SSE projection over five durable low-volume event kinds: state change, execution start, coalesced progress, verified artifact availability, and execution completion.

Allocate a monotonic per-run sequence durably and use its decimal value as the SSE `id`. Resume strictly after `Last-Event-ID`. Heartbeats are unsequenced comments. Retain the complete sequence for a bounded initial window of 24 hours after terminal completion; a cursor older than retained history receives 410 Problem Details and resynchronizes through run/results/artifacts. Deliver the terminal event and close. Re-authorize every connection; bearer headers or a same-site Secure HttpOnly session cookie are allowed, never query tokens.

## Alternatives considered

- WebSockets for bidirectional communication.
- Polling only.
- SSE with no replay.
- Infinite replay of raw log/step events.

## Why alternatives were rejected

The MVP needs no client-to-server channel after connection, so WebSockets add operational complexity. Polling remains a fallback but is inefficient for progress. No-replay SSE loses events during ordinary reconnects. Infinite/high-volume replay has unbounded cost and expands the hostile-output surface.

## Consequences

### Positive

- Native HTTP one-way semantics with deterministic reconnect and gap behavior.
- Bounded durable history and low event volume.
- Canonical API resources remain the resynchronization source of truth.

### Negative

- Requires durable per-run sequence allocation and retention storage.
- Native browser EventSource authentication constrains session design.
- Proxies, connection limits, reauthorization windows, and cleanup need integration tests.

### Neutral

- Detailed steps live in structured results and logs live as bounded artifacts, not browser events.

## Validation and revisit conditions

Validate reconnect, 410 gap, terminal close, 204 post-terminal cursor, cookie/bearer authorization, Origin/CORS, heartbeat, proxy buffering, connection limits, and event budget before promotion. Revisit if measured client needs require bidirectional controls or a different retention window.
